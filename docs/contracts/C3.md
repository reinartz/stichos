## 1. Scope

This contract defines the diagnostic code system used across all stichos crates. Every error,
warning, hint, info, and fatal message produced by any stichos component must carry a
**stable prefixed code** registered in the `gp-core` `DiagnosticRegistry`.

## 2. Code format

Every diagnostic code has the form:

```
PREFIX-CATnnn
```

Where:
- `PREFIX` is 2–4 uppercase letters identifying the crate family
- `CAT` is 1–3 uppercase letters identifying the error category (E = error, W = warning, F = fatal, etc.)
- `nnn` is 3 or more digits

**Pattern:** `^PREFIX-[A-Z]{1,3}-\d{3,}$`

### Crate family prefixes

| Prefix | Crate | Description |
|--------|-------|-------------|
| `GP` | gp-core | Core types, IR validation, general errors |
| `OOX` | adapters-ooxml | Open XML / OPC / Office document errors |
| `ODF` | adapters-odf | OpenDocument Format errors |
| `PDF` | adapters-pdf | PDF parsing and structure errors |
| `ENG` | engines | Engine lifecycle and capability errors |
| `LIN` | lint | Layout, font, and quality lint errors |
| `CLI` | cli | Command-line argument and I/O errors |
| `MCP` | mcp | MCP transport and JSON-RPC errors |

## 3. Severity levels

| Severity | Constant | Meaning |
|----------|----------|---------|
| `hint` | `Severity::Hint` | Suggestion, no action required |
| `info` | `Severity::Info` | Informational, no action required |
| `warning` | `Severity::Warning` | Something may be wrong but processing continues |
| `error` | `Severity::Error` | Something is wrong; diagnostic should be reported |
| `fatal` | `Severity::Fatal` | Unrecoverable — the process will exit |

**Severity ordering:** `hint < info < warning < error < fatal`

### Fatal vs Error semantics

- **Fatal** — unrecoverable; the process must exit after reporting the diagnostic.
- **Error** — a diagnostic that should be reported to the user but does not force a process exit.

## 4. JSON output format

All diagnostics are emitted as a JSON envelope:

```json
{
  "diagnostics": [
    {
      "code": "GP-E001",
      "severity": "error",
      "message": "Invalid IR version: expected 1.0 but found 2.0",
      "span": {
        "offset": 0,
        "length": 3
      }
    }
  ]
}
```

The `span` field is optional and omitted when not available.

### Envelope type

```rust
pub struct DiagnosticEnvelope {
    pub diagnostics: Vec<Diagnostic>,
}
```

## 5. No ad-hoc error strings

**Rule:** No ad-hoc error strings in user-visible output. All diagnostics go through the registry.

Every `Diagnostic` struct must have a `code` that exists in `DiagnosticRegistry::instance()`.
Ad-hoc codes (codes not in the registry) are treated as `Warning` severity and never produced
in production paths.

### Enforcement

- **Code-uniqueness test:** The registry must not contain duplicate codes.
- **Serde snapshot test:** Serializing known diagnostics and round-tripping must produce identical structures.
- **No-ad-hoc-strings lint gate:** CI must verify that every code referenced in tests matches the registry.

## 6. Code lifetime rules

- Codes are **never** reused or reassigned.
- New codes are **additive only**.
- When a code is removed (deprecated), its slot is reserved — the code string stays in the
  registry with a `deprecated` flag but is never recycled for a new purpose.

## 7. Consumer crate responsibilities

Each consumer crate (adapters-ooxml, adapters-odf, adapters-pdf, engines, lint) uses its own
code prefix exclusively:

| Crate | Allowed prefixes |
|-------|-----------------|
| `adapters-ooxml` | `OOX-` |
| `adapters-odf` | `ODF-` |
| `adapters-pdf` | `PDF-` |
| `engines` | `ENG-` |
| `lint` | `LIN-` |
| `cli` | `CLI-` |
| `mcp` | `MCP-` |
| `gp-core` | `GP-` |

## 8. CLI rendering format

The CLI renders diagnostics with:

```
[SEVERITY] CODE: message
```

Example output:
```
[ERROR] OOX-E001: OPC validation failed: missing [Content_Types].xml
[WARN]  GP-W001: Unknown element 'w:custom' in IR — ignored
[FATAL] OOX-E004: Path traversal detected in package entry: ../../etc/passwd
```

## 9. Error model

The `ReadError` enum covers all reader failure paths:

| Variant | Primary code | Source |
|---------|-------------|--------|
| `OpcError` | `OOX-E001` | OPC validation/parsing |
| `XmlError` | `OOX-E002` | XML parsing |
| `PdfError` | `PDF-E001` | PDF parsing |
| `OdfError` | `ODF-E001` | ODF package |
| `EngineError` | `ENG-E001` | Engine lifecycle |
| `LinterError` | `LIN-E001` | Layout linting |
| `IoError` | `CLI-E002` | Standard I/O |
| `SerdeError` | `GP-E001` | Deserialization |
| `Unknown` | `GP-W001` | Unclassified |

Each `ReadError` implements:
- `From<std::io::Error>` — wraps `IOError`
- `From<serde_json::Error>` — wraps `SerdeError`
- `std::fmt::Display` — `[CODE]: detail` format
- `std::error::Error` — standard trait
- `to_diagnostics()` — converts to 1..N `Diagnostic` items

## 11. Conformance tests

The following tests must pass in `gp-core`:

1. **Code uniqueness:** Iterate all codes; verify no duplicates.
2. **Serde snapshot:** Serialize known diagnostics, round-trip, compare.
3. **Error-to-diagnostic conversion:** `ReadError` → diagnostic list produces correct codes/severities.
4. **JSON envelope shape:** Serializing a diagnostic list produces `{"diagnostics": [...]}`.
5. **Code lookup:** `from_str` returns `Some` for valid codes, `None` for invalid.
6. **Display format:** CLI rendering produces `[SEVERITY] CODE: message` format.
7. **Pattern validation:** All registered codes match `^PREFIX-[A-Z]{1,3}-\d{3,}$`.
8. **No ad-hoc strings:** Every code in tests references the registry.

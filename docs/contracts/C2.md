## 1. Scope
Defines how element IDs are derived, stored, and used in the IR.

## 2. ID format
- Format: `id-<hex_prefix>` where hex_prefix is the first 12 hex chars of SHA-256(kind + "/" + path + "/" + content_hash)
- Content hash = SHA-256 of the element's canonical JSON serialization (minified, no spaces)
- Total ID length: ~16 characters

## 3. Read-stability (M1 requirement)
- Same input document -> same element IDs across all sessions
- Deterministic ordering of elements within containers
- Survives IR serialize -> deserialize round-trip

## 4. Edit-stability
- IDs survive content-preserving edits (text changes, style changes)
- IDs change only when element structure changes (insert/delete/reorder)
- Unchanged nodes keep their original IDs across patch application
- Touched nodes get a new content-hashed ID (same path, different hash)
- Anchor healing: parent IDs are preserved when only children change

## 5. Anchor Healing
- When an element's children change but the element itself does not, the parent's ID is preserved
- `anchor_heal` re-derives parent ID from children's content hashes
- `verify_anchor_heal` validates that parent IDs are preserved across transformations

## 6. ID Map
- Every IRDocument carries an `IdMap` of all element IDs -> metadata
- IdMap is serializable
- Consumers use IdMap for element lookup by path

## 7. Collision guarantee
- 12-hex = 48 bits -> collision probability < 10^-12 for up to 100k elements
- If corpus exceeds 100k elements, increase prefix to 16 hex chars

## 8. Conformance
- Property test: same input -> same IDs
- Property test: survives reparse
- Property test: random patch sets never renumber untouched elements
- Property test: touched nodes keep ID with content-hash roll
- Property test: anchor healing works on parent elements
- Collision sweep over corpus

## 9. Freeze Notice
This contract is frozen at version 1.0.0 as of 2026-09-14.
Changes require a new version bump and phase-gate approval.
